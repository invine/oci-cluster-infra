# Disaster-recovery manual-actions audit

Date: 2026-08-04

## Question and verdict

Requirement: rebuilding the same cluster from scratch must require no operator actions other than Terraform apply, manual synchronization of Argo CD child Applications, and a manual Velero restore.

**Verdict: the current configuration does not satisfy that requirement literally.** A clean rebuild is automated once its execution environment and several durable external inputs already exist, but those inputs cannot be reconstructed from the repositories. At minimum, an operator must recover/populate the two ignored tfvars files and the referenced OCI API private key, run Terraform initialization, and ensure the external Velero bucket and its IAM access survived. Both authoritative Terraform states are also local-only. Longhorn's host prerequisites are not enforced, and OCI Customer Secret Key exhaustion can require manual remediation.

If “manual actions” means only actions during a DR event and the recovery workstation, secret-value archive, OCI identity/policies, DuckDNS account, Git repositories, container registries, and external backup bucket are all explicitly treated as pre-provisioned DR dependencies, then the intended steady-state sequence can be reduced to the permitted actions. That stronger prerequisite contract is not currently codified or tested.

## Scope and classification

- **Definitely manual**: required by the checked-in procedure or required data is deliberately outside both Terraform states.
- **Conditionally manual**: Terraform attempts the work, but a fresh environment can require remediation because the prerequisite is not declared or verified.
- **Automatically handled**: represented in Terraform/Argo configuration and reachable through the intended bootstrap chain.

This audit used current working-tree source, including uncommitted configuration. It also followed the Medusa Application into `/Users/invine/src/js/my-medusa-store`, because that repository is an Argo source. No infrastructure was changed or applied.

3. **Platform apply (automatic after kubeconfig).** All Kubernetes/Helm/kubectl providers consume the generated kubeconfig (`/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/providers.tf:36-58`; `/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/variables.tf:31-35`). Terraform installs NGINX Ingress, cert-manager and its ClusterIssuer, Longhorn, Velero, and Argo CD.
4. **DNS and certificates (attempted automatically).** The NGINX Service requests an OCI load balancer (`/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/nginx-ingress-controller.tf:7-45`). A local-exec calls DuckDNS with the resulting IP (`/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/duckdns.tf:1-10`). cert-manager creates the ACME account key and workload certificates as generated resources (`/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/cert-manager.tf:1-38`; `/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/argocd.tf:14-34`).
5. **Argo bootstrap (automatic root, manual children).** Terraform installs Argo CD, registers the public bootstrap repository, and creates an auto-syncing `argocd-bootstrap` Application (`/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/argocd.tf:1-87`). The root graph creates the AppProject, four namespaces, the Medusa repository registration, and four child Applications; waves put the project/namespaces/repository before child Application creation (`/Users/invine/src/oracle-cluster/k8s-charts/argocd-bootstrap/root/namespaces/applications.yaml:1-39`; `/Users/invine/src/oracle-cluster/k8s-charts/argocd-bootstrap/root/projects/application-workloads.yaml:1-24`; `/Users/invine/src/oracle-cluster/k8s-charts/argocd-bootstrap/root/repositories/medusa-store.yaml:1-16`; `/Users/invine/src/oracle-cluster/k8s-charts/argocd-bootstrap/root/applications/medusa-staging.yaml:1-19`). Child Applications have no automated sync policy, matching the permitted manual-sync step.
6. **Explicit secrets (automatic only if values were recovered manually).** Terraform waits up to five minutes for Argo to create all four namespaces and then creates the Medusa, GHCR, and Vaultwarden secrets (`/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/application-secrets.tf:1-84`). There is no OCI Vault or external-secrets dependency: local tfvars are the Secret Value Authority (`/Users/invine/src/oracle-cluster/local-oci-cluster-infra/docs/adr/0002-terraform-owns-explicit-secrets.md:1-3`).
7. **Velero readiness (automatic only if external dependencies survived).** Terraform creates a fresh OCI Customer Secret Key, installs Velero with the AWS S3 plugin, configures the external bucket, deploys the node agent, installs the preserved repository password, and creates restore-action ConfigMaps (`/Users/invine/src/oracle-cluster/local-oci-cluster-infra/platform/velero.tf:1-110`).
8. **Restore and workload reconciliation (manual, permitted, but order-sensitive).** Restore must occur after platform/Velero/Longhorn and the application namespaces are ready, and normally before syncing stateful child Applications. Velero FSB dynamically provisions replacement PVs from restored PVCs; syncing first can create resources that Velero subsequently skips as already existing. After restore, manually sync the four child Applications so Git desired state reconciles restored resources. The stateful pods are opted into FSB (`/Users/invine/src/oracle-cluster/k8s-charts/openvpn-chart/templates/deployment.yaml:19-45`; `/Users/invine/src/oracle-cluster/k8s-charts/vaultwarden-chart/templates/deployment.yaml:17-51`; `/Users/invine/src/js/my-medusa-store/charts/medusa/templates/postgres.yaml:40-46`; `/Users/invine/src/js/my-medusa-store/charts/medusa/templates/redis.yaml:40-46`; `/Users/invine/src/js/my-medusa-store/charts/medusa/templates/backend.yaml:40-48`). Official Velero 1.14 documentation confirms that FSB restores use dynamic PV provisioning and require the restored pod/PVC path: <https://velero.io/docs/v1.14/file-system-backup/> and <https://velero.io/docs/v1.12/restore-reference/>.

### Automatically handled

- OCI compartment, network, cluster, node pool, SSH key, and kubeconfig generation are Terraform-managed.
- Shared platform namespaces and Helm releases (NGINX, cert-manager, Longhorn, Velero, Argo CD) are Terraform-managed.
- The Argo bootstrap repository registration and Bootstrap Seed are Terraform-managed; root reconciliation is automatic.
- Application namespaces are auto-created by the root graph, and Terraform waits for them before materializing Explicit Secrets.
- Velero's Kubernetes credential Secret, repository-password Secret, BackupStorageLocation configuration, node agent, and restore-action ConfigMaps are produced by the platform apply. The bucket and permissions are not.
- DuckDNS is attempted during apply, and cert-manager handles ACME account/certificate generation when DNS and external services work.
- Application manifests declare Longhorn PVCs, FSB opt-in annotations, and Velero Schedules. Their creation is correctly deferred to the permitted manual child-Application sync.

## Important restore behavior

The practical DR order should be treated as part of the allowed “manual Velero restore” operation:

1. Apply `infra`, then apply `platform`.
2. Confirm nodes, Longhorn, Velero node agents, and BackupStorageLocation are ready and the old backups are visible.
3. Restore the selected backup(s) **before** child Applications create the stateful workload objects.
4. Wait for Velero Restore and PodVolumeRestore completion.
5. Manually sync the four child Applications and verify health/certificates/endpoints.

This is not currently documented or machine-checked. In particular, the Platform apply creates current Explicit Secrets before restore; Velero normally skips already-existing Secrets. That is safe only if the recovered tfvars contain the exact intended current values. The chart-level schedules cover the application namespaces and disable snapshots (`/Users/invine/src/oracle-cluster/k8s-charts/openvpn-chart/templates/velero-schedule.yaml:8-15`; `/Users/invine/src/oracle-cluster/k8s-charts/vaultwarden-chart/templates/velero-schedule.yaml:9-18`; `/Users/invine/src/js/my-medusa-store/charts/medusa/templates/velero-schedule.yaml:9-16`), while pod annotations opt the persistent volumes into FSB.

## Validation performed and limits

- `helm lint echo-chart openvpn-chart vaultwarden-chart` passed all three charts.
- Static source tracing found no additional shell/provisioner path beyond the `kubectl wait` and DuckDNS `curl` local-exec calls.
- Both Terraform roots validated successfully in a normal local execution context. A parallel sandbox attempt could not start the already-downloaded provider binaries, but that sandbox-only plugin-handshake failure produced no HCL diagnostic.
- Live read-only checks on 2026-08-04 found the `default` BackupStorageLocation `Available` and all schedules `Enabled`. The latest 2026-08-03 scheduled backups for echo, Medusa, and Vaultwarden were `Completed`; the OpenVPN scheduled backup was `PartiallyFailed` with one error. A later manual backup, `ovpn-fresh-full-20260803152134`, was `Completed`. There were no `restores.velero.io` objects, so the live cluster contains no recorded evidence of an end-to-end restore test. This makes OpenVPN scheduled-backup reliability and the untested restore sequence current operational risks, not merely theoretical ones.
- No live OCI/Kubernetes mutation or destructive DR test was performed. Therefore cross-cluster bucket access with a newly generated key, actual node packages on newly created workers, and end-to-end restore correctness remain unproven.

## Bottom line

The repository automates the cluster and platform bootstrap well enough that a prepared operator can likely perform DR with two Terraform applies, one or more Velero restores, and child Application syncs. It is **not self-contained enough to guarantee “only those actions” from scratch**. The blocking gaps are recoverable secret/input artifacts, local-only Terraform states, Terraform initialization/tooling, the deliberately external bucket and IAM policy, and unverified Longhorn/Velero prerequisites. The current OpenVPN scheduled backup is partially failed and no restore test is recorded; likely surprise remediations include OCI Customer Secret Key exhaustion and failed DNS/node prerequisites.
